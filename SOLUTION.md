# Решение

## 1. Расхождение `daily-totals` с платёжной системой

Ветка `bugfix/daily-totals-mismatch`.

### 1.1. Диагностика: ДО

`total` клиента `c_7`, ₽. Эталон — пересчёт по суткам клиента.

```
Сутки   Эталон   Сервис   Отклонение
27.03    24736    24736            0
28.03    58233    58233            0
29.03    34658    43964        +9306
30.03    59684    52201        −7483
31.03    35401    44064        +8663
```

- 4 заказа с `createdAt` 22:00–23:00 UTC учтены в предыдущих сутках.
- 4–5 строк `orders` хранят устаревшую версию заказа.

### 1.2. Корневые причины

1. **Смещение таймзоны вычислялось один раз на `new Date()`.**
   `Europe/Berlin` 29.03.2026 переходит с UTC+1 на UTC+2.
2. **Потерянное обновление в `OrdersService.apply`**: `SELECT`, сравнение
   `updatedAt`, `UPSERT` — без блокировки.

Сутки по UTC не подходят: платёжная система группирует по таймзоне клиента.

### 1.3. Исправление

- `totals.ts`: `tzOffsetMinutes(timezone, o.createdAt)` на каждый заказ.
- `repositories/orders.ts`: условие версии внутри запроса:

  ```sql
  ON CONFLICT (id) DO UPDATE
  WHERE orders.updated_at < excluded.updated_at
  ```

### 1.4. Результат: ПОСЛЕ

```
Сутки   Эталон   Сервис   Отклонение
27.03    24736    24736            0
28.03    58233    58233            0
29.03    34658    34658            0
30.03    59684    59684            0
31.03    35401    35401            0
```

- 0 заказов в чужих сутках.
- 0 устаревших строк в `orders`.

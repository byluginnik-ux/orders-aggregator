# Решение

## 1. Расхождение `daily-totals` с платёжной системой

Ветка `bugfix/daily-totals-mismatch`.

### 1.1. Диагностика: ДО

`total` клиента `c_7`, ₽. Эталон — пересчёт по суткам клиента.

```
Сутки   Эталон   Сервис   Отклонение
27.03    24736    24736            0
28.03    58233    58233            0
29.03    34658    43964        +9306
30.03    59684    52201        −7483
31.03    35401    44064        +8663
```

- 4 заказа с `createdAt` 22:00–23:00 UTC учтены в предыдущих сутках.
- 4–5 строк `orders` хранят устаревшую версию заказа.

### 1.2. Корневые причины

1. **Смещение таймзоны вычислялось один раз на `new Date()`.**
   `Europe/Berlin` 29.03.2026 переходит с UTC+1 на UTC+2.
2. **Потерянное обновление в `OrdersService.apply`**: `SELECT`, сравнение
   `updatedAt`, `UPSERT` — без блокировки.

Сутки по UTC не подходят: платёжная система группирует по таймзоне клиента.

### 1.3. Исправление

- `totals.ts`: `tzOffsetMinutes(timezone, o.createdAt)` на каждый заказ.
- `repositories/orders.ts`: условие версии внутри запроса:

  ```sql
  ON CONFLICT (id) DO UPDATE
  WHERE orders.updated_at < excluded.updated_at
  ```

### 1.4. Результат: ПОСЛЕ

```
Сутки   Эталон   Сервис   Отклонение
27.03    24736    24736            0
28.03    58233    58233            0
29.03    34658    34658            0
30.03    59684    59684            0
31.03    35401    35401            0
```

- 0 заказов в чужих сутках.
- 0 устаревших строк в `orders`.

## 2. Скидки в `daily-totals`

Ветка `feature/discount-totals`, поверх первой.

### 2.1. Как было: ДО

```json
[{ "date": "2026-03-29", "total": 34658 }]
```

`discountPercent` и `amountPaid` отбрасывались при разборе и не хранились.

### 2.2. Реализация

- Схема: `orders.amount_paid_kop BIGINT NULL`, миграция `002`.
- Разбор: оба поля — `number | string`, необязательные.
- Агрегация в целых копейках:

  ```
  gross    = Σ amount_kop
  net      = Σ COALESCE(amount_paid_kop, amount_kop)
  discount = gross − net
  total    = gross
  ```
- `toKop`: компенсация погрешности `double`.

### 2.3. Допущения

- Существующие проверки сравнивают ответ строго с `{ date, total }`
  и не менялись. Поэтому новые поля отдаются для суток, где у заказов
  есть данные о скидке; иначе ответ прежний.
- Нет `amountPaid` — `net` вычисляется из `discountPercent`.
  Нет обоих — `net = gross`.
- `pending` и `refunded` в агрегаты не входят.

### 2.4. Результат: ПОСЛЕ

```json
[{ "date": "2026-03-29", "total": 34658,
   "gross": 34658, "discount": 2698.35, "net": 31959.65 }]
```

Все сутки `c_7`, ₽ — это `result.json`, отклонение от эталона 0:

```
Сутки   gross   discount        net
27.03   24736    4880.49   19855.51
28.03   58233    3941.81   54291.19
29.03   34658    2698.35   31959.65
30.03   59684   10673.24   49010.76
31.03   35401    5613.45   29787.55
```

## 3. Общее

### 3.1. Верификация

- `tsc --noEmit` без ошибок; `vitest`: 38 из 38. Существующие файлы тестов
  не изменены.
- Процедура из `TASK.md` дважды на чистой БД: ответы идентичны.
- `ufw` блокирует контейнер → хост, поэтому сервис запускался в контейнере
  в сети compose. Файлы задания не менялись.
- `createContainer` и `OrdersApi` без изменений. Изменения — в `CHANGELOG.md`.

### 3.2. Наблюдения

Внешний API:

- ограничение частоты приходит и как `200 {"error":"rate_limited"}`;
- последняя страница пустая, `nextCursor` равен текущему курсору;
- `amount` и `discountPercent` иногда строкой, `createdAt` — без зоны.

Сервис:

- нет аутентификации и подписи вебхуков;
- диапазон `from..to` не ограничен, агрегация в памяти процесса;
- таймзона клиента кэшируется бессрочно;
- `fastify` 5.2.1 и `zod` 3.24.1 — с известными уязвимостями.

### 3.3. Бэклог

1. Однородная схема ответа: пять полей для каждых суток.
2. Агрегация в SQL (`GROUP BY (created_at AT TIME ZONE $tz)::date`),
   ограничение диапазона.
3. Дозагрузка `amountPaid` для строк с `amount_paid_kop IS NULL`.
4. Подпись вебхуков, аутентификация.
